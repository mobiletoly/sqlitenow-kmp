It first drives ordinary settlement and acknowledgment under the old source, then requests the rotated snapshot. Inside the final writer, after the snapshot is installed and verified, it requeues every pending edit as dirty intent. An edit made from the server state the snapshot still holds is rebased onto the installed observation of its key. An edit whose row another source updated or deleted, or whose key another source created, after the edit was made keeps its original operation and historical base, so its upload is refused as an ordinary `push_conflict` for the configured resolver and never overwrites that change. The writer then writes each local value back to the business row and releases the retired source's frozen request, retained rejection and acknowledgment obligation. The next ordinary push freezes that intent as the replacement source's first bundle. Intent that violates a foreign key or uniqueness constraint against the snapshot, or a stale edit without a valid original base to keep, rolls the installation back and raises `PendingIntentUnsatisfiableException`. `discardPendingIntentForRecovery()` is the only discard: it is explicit, reports exactly the dropped rows, requires the staged replacement snapshot while an upload journal exists, and never runs implicitly.
